## The Hard Blockers First — Architecture Gaps

Before any feature work, two structural decisions must be made. Everything else depends on them.

### Gap 0-A — ID Type Mismatch (Critical)

| System | ID format | Example |
|---|---|---|
| Old DB (production) | CUID string | `clxyz3f4k0000abc123def456` |
| New DB | Integer SERIAL | `1`, `42`, `1891` |

Every single table, every foreign key, every API response references these IDs differently. A data migration must either:

- **Option A** — Transform all CUIDs to integers during migration (complex, requires full ID remapping across all tables)
- **Option B** — Change new server schema to use `TEXT` primary keys (simpler data migration, requires updating 12+ migration files and all raw SQL queries in routes)

**Recommendation: Option B.** Changing ID types in the schema is safer than building a cross-table ID remapping engine for 45 tables of live data.

---

### Gap 0-B — Payment Provider Mismatch ✅ CLOSED

**Resolution: No action required.** Paymob was never successfully integrated in the old codebase — no real payment transactions were processed. There are no Paymob `providerRef` records in the old DB to preserve or migrate. Fawaterak is the only active provider going forward.

**Side-fix applied:** `billing.js` callback route had `Number(paymentId)` leftover from integer IDs — converted to NaN with CUID strings, preventing payment activation. Removed the `Number()` cast (lines 26, 29).

## Priority 1 — Must Have Before Migration (Blockers)

These features have **active users depending on them right now**. Migration cannot proceed until all P1 items exist in the new codebase.

---

### P1-1 — Forgot Password / Reset Password Flow

**Status: Missing in new client and server**

Old routes:
- `POST /auth/forgot-password` → sends email with reset code
- `POST /auth/reset-password` → verifies code, sets new password

Old client pages:
- `/forgot-password`
- `/check-mail`
- `/reset-password`

New server: No forgot-password endpoint exists in `server/routes/auth.js`.
New client: No forgot-password or reset-password pages exist.

**Impact:** Any user who forgets their password is permanently locked out after migration.

**What to build:**
- Server: `POST /auth/forgot-password` — generate 6-digit code, store in `password_reset_tokens` table, send email
- Server: `POST /auth/reset-password` — verify code, update `users.password_hash`
- Client: `/forgot-password` page, `/check-mail` confirmation page, `/reset-password` page

---


### P1-2 — Email Verification Flow

**Status: Missing in new client and server**

Old DB has `emailVerified`, `emailVerificationCode`, `emailVerificationCodeExpiresAt` fields on `User`.

Old client pages:
- `/verify-email-required` — gate page shown to unverified users

New server: No email verification logic in `server/routes/auth.js`. No relevant columns in new `users` table.

**Impact:** If `AppConfig.requireEmailVerification` is enabled in the old system, migrated users who haven't verified email will be blocked on the new system with no path to verify.

**What to build:**
- Add `email_verified`, `email_verification_code`, `verification_code_expires_at` columns to `users` migration
- Server: `POST /auth/send-verification` and `POST /auth/verify-email` endpoints
- Client: `/verify-email-required` gate page

---

### P1-3 — Client-Coach Messaging (Thread + Message)

**Status: Completely absent in new codebase**

Old has a full real-time messaging system:
- `Thread` model (one thread per client)
- `Message` model (with `senderType`, `body`, `attachments`, read receipts `readByTeamAt` / `readByClientAt`)
- Socket.io real-time delivery
- Old dashboard page: `/dashboard/messenger`
- Old client portal page: `/client/support`

New server: No threads, no messages, no Socket.io.
New client: No messenger page, no support page.

Old API routes missing:
```
GET    /messenger/inbox
GET    /messenger/threads/:threadId/messages
POST   /messenger/threads
POST   /messenger/threads/:threadId/messages
PATCH  /messenger/threads/:threadId/status
GET    /clients/client/threads
POST   /clients/client/threads
POST   /clients/client/threads/:threadId/messages
```

**Impact:** All existing message history is inaccessible. Coaches and clients lose their communication channel.

**What to build:**
- DB: `threads` and `messages` tables (with read receipt timestamps)
- Server: full messenger routes (team-side + client-side)
- Server: Socket.io integration for real-time delivery
- Client: `/[workspaceSlug]/messenger` dashboard page
- Client portal: `/portal/support` or `/portal/messages` page

### P1-4 — Workout Logs (Client Training History)

**Status: Missing in new codebase**

Old has `WorkoutLog` model — every completed workout session is recorded:
- `clientId`, `planId`, `dayIndex`, `date`, `exercises` (JSON), `completed`, `notes`
- Old dashboard page: `/dashboard/workout-logs`
- Client can log workouts from portal

Old API routes missing:
```
GET  /workout/logs
GET  /workout/logs/:id
POST /workout/logs   (client submits completed session)
```

New server: No workout log table or routes.
New client: No workout-logs page.

**Impact:** All client workout history is lost on migration. Clients lose their training timeline.

**What to build:**
- DB: `workout_logs` table with `client_id`, `plan_id`, `day_index`, `date`, `exercises` JSONB, `completed`, `notes`
- Server: GET + POST routes for workout logs (both coach and client access)
- Client: `/[workspaceSlug]/workout-logs` page (coach view)
- Client portal: workout logging button/flow on training plan page

### P1-5 — Push Notifications (FCM)

**Status: Completely absent in new codebase**

Old uses Firebase Admin SDK to send push notifications to client devices:
- `Client.deviceToken` stores the FCM token
- `POST /push-notifications/send` — coach sends push notification
- `POST /clients/device-token` — client registers FCM token
- Old dashboard page: `/dashboard/push-notifications`

New server: No Firebase SDK, no device token storage, no push route.
New client: No push-notifications page.

**Impact:** Clients stop receiving push notifications for new plans, messages, form assignments on day 1 of migration.

**What to build:**
- Add `device_token` column to `clients` table migration
- Server: integrate `firebase-admin` SDK
- Server: `POST /clients/device-token` — save FCM token
- Server: `POST /push-notifications/send` — send to one or all clients
- Client: `/[workspaceSlug]/push-notifications` page

**Impact:** Clients cannot renew or start subscriptions after migration.

**What to build:**

- Server: payment webhook handler for Fawaterak confirming subscription activation
- Client: payment success/failure pages

### P1-7 — Food Replacement Request Flow (Client-Facing)

**Status: Partially present (coach side only)**

Old has a two-sided food replacement workflow:
- Client submits a replacement request (`POST /nutrition/replacements/request`)
- Client views their pending/approved requests (`GET /nutrition/replacements/my-requests`)
- Coach reviews and approves/modifies (`PUT /nutrition/replacements/:requestId/process`)
- Client receives notification of coach decision

New server has food replacements on the coach side (`/requests` routes in `clientPortal.js`) but the full client-to-coach approval loop needs verification.

**What to verify and complete:**
- Client can submit a food swap request from their nutrition plan
- Coach sees pending requests in nutrition dashboard
- Coach can approve, reject, or modify with notes
- Client receives in-app notification of the decision

### P1-8 — Team Invitation: Email-Based Accept Flow

**Status: Partially present**

Old flow: coach invites team member by email → invitation email sent → recipient clicks link → `/team/invitation/[token]` page → accepts and joins workspace.

New server has `workspace_invitations` table and routes. New client has `/[workspaceSlug]/team` page.

**Gap:** The invitation accept page at `/team/invitation/[token]` needs to exist in the new client and handle the token → account creation or login → workspace join flow.

**What to verify:**
- `GET /invitations/invite/:token` returns invitation details
- New client has a `/team/invitation/[token]` page that handles acceptance
- If the invited user doesn't have an account yet, they can create one during acceptance
