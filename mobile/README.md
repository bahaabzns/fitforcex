# FitForce — Mobile (Flutter Client App)

Native iOS + Android client app that mirrors the web **client portal** (`client/app/(client)/portal/*`) and consumes the same backend API (`/api/client-portal/*`). See [`docs/_FlutterClientApp.md`](../docs/_FlutterClientApp.md) for the full build plan.

## Status: Phase 0 — Spine

The Dart source spine is hand-authored and runnable **after** the SDK is installed and the native platform folders are generated.

## First-time setup

This folder contains the `lib/` source, `pubspec.yaml`, and config, but **not** the native `android/` + `ios/` folders (those are generated by the Flutter tool).

```bash
# 1. Install Flutter SDK (stable), then from this folder:
cd mobile

# 2. Generate the native platform folders WITHOUT overwriting lib/ or pubspec:
flutter create . --org com.fitforcex --project-name fitforce_x \
  --platforms=android,ios

# 3. Fetch packages
flutter pub get

# 4. Generate localizations (reads l10n.yaml + lib/l10n/*.arb)
flutter gen-l10n

# 5. Codegen for freezed/json models
dart run build_runner build --delete-conflicting-outputs

# 6. (Re)generate launcher icon + native splash from assets/icon/app_icon.png
dart run flutter_launcher_icons
dart run flutter_native_splash:create

# 7. Run (Android emulator example — host API on 10.0.2.2)
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:5000 --dart-define=FLAVOR=dev
```

> `flutter create .` is safe to run over this folder — it only adds the missing native folders and tooling; it won't clobber existing `lib/` files or `pubspec.yaml`.

## Configuration

All build-time config comes through `--dart-define` (dev: see [`.env.example`](.env.example)) or `--dart-define-from-file` (release: [`env.prod.json`](env.prod.json)), read in one place: `lib/core/config/app_config.dart`. No `process.env`-style reads anywhere else.

| Key | Meaning |
|---|---|
| `API_BASE_URL` | API origin, no trailing slash. App appends `/api/client-portal/*`. |
| `FLAVOR` | `dev` \| `staging` \| `prod` |
| `DEFAULT_WORKSPACE_SLUG` | Dev-only prefill for the login workspace field. |

## Architecture

Feature-first, layered (mirrors the backend `modules/` discipline):

```
lib/
├── main.dart / app.dart      # bootstrap + MaterialApp.router
├── core/                     # config, network, auth, router, theme, i18n, widgets
├── features/                 # one folder per screen group
├── l10n/                     # ARB source (en/ar) → generated AppLocalizations
└── shared/                   # models + ported utils (added in later phases)
```

## Phase 0 conventions (codegen-free)

To keep the spine buildable with just `pub get`, Phase 0 uses **manual** Riverpod providers, **hand-written** models, and **gen-l10n** (built into the SDK). `freezed` / `json_serializable` / `riverpod_generator` come online in Phase 2 when model complexity grows.

## Backend dependency

Token auth (bearer in the `/client-portal/login` response body) is **backend change #1** in the plan (§12). Until it lands, login can't complete against the current cookie-only endpoint. The client code is written for bearer and degrades gracefully if `token` is absent.

## Release signing (Android)

Release builds are signed from `android/key.properties` (gitignored). Without it,
a release build falls back to debug keys (not publishable). To produce a real
release artifact:

```bash
# 1. Create an upload keystore (once)
keytool -genkey -v -keystore upload-keystore.jks -storetype JKS \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload

# 2. Copy the template and fill in passwords + absolute storeFile path
cp android/key.properties.example android/key.properties

# 3. Build a signed release — always via env.prod.json, never bare --dart-define
# flags typed by hand. A release build with no FLAVOR/API_BASE_URL set falls
# back to the dev/emulator config and refuses to launch (see AppConfig.fromEnvironment).
flutter build appbundle --release --dart-define-from-file=env.prod.json
```

Never commit `key.properties` or the `.jks` — both are gitignored. `env.prod.json`
holds no secrets (just the public API origin + flavor), so it **is** committed.

## Native flavors (follow-up)

Dart-level flavors work today via `FLAVOR`. Native product flavors / Xcode schemes (distinct app ids per env) are wired after `flutter create` generates the platform folders — tracked as a Phase 0 follow-up.
